## The Reality Check: Consolidating Your Tracks

Your current list contains five parallel tracks (Math, Graphics APIs, Projects, Language, and DSA). Attempting all of these simultaneously will cause context-switching fatigue and slow down your long-term retention. To realistically achieve your goals in 12 months, you need to streamline and sequence them:

* **Postpone Vulkan:** Do not touch Vulkan yet. Vulkan requires explicit memory management and verbose pipeline state setup. Learning it while simultaneously trying to grasp C++ syntax and fundamental graphics theory will lead to massive frustration. Master the pipeline concepts in OpenGL first.
* **Trim the Math and DSA:** Drop *How to Prove It* unless your goal is formal academic research. Game engines require linear algebra and vector calculus, not formal logic proofs. Choose **one** platform for your daily code exercises (e.g., LeetCode) rather than splitting your focus across three.

* **Why it works:** Writing a ray tracer in pure, CPU-bound C++ forces you to master pointers, memory management, and linear algebra (vector math, ray-object intersection) before dealing with the complexity of a GPU driver.
* **Portfolio Deliverable:** A standalone, CPU-based C++ Software Ray Tracer that renders spheres, shadows, and reflections.

* **Core Focus:** *LearnOpenGL* (Core Profile), *CMU 15-462* lectures (match video topics directly to what you are currently building, e.g., Rasterization, Transformations, Textures), and James Stewart’s *Calculus* (specifically 3D Coordinate Geometry and Vectors chapters).

* **Portfolio Deliverable:** A 3D Scene Viewer/Mini-Engine base. It must load 3D assets (via Assimp), implement a custom scene graph, and feature real-time lighting (Blinn-Phong) and shadow maps.

### Phase 3: Months 8–10 — Spatial Architectures & Optimization

* **Core Focus:** Continue *CMU 15-462* (specifically spatial data structures and geometry processing chapters) and apply it directly to expand your engine.
* **Why it works:** A true game engine requires structural management to handle complex scenes efficiently.
* **Portfolio Deliverable:** Upgrade your Phase 2 Mini-Engine. Integrate View Frustum Culling, a spatial partitioning system (like an Octree or BVH) for faster rendering/collision detection, and a post-processing pipeline (e.g., Bloom or HDR).

### Phase 4: Months 11–12 — Low-Level Graphics (Vulkan Transition)

* **Core Focus:** The official Vulkan Tutorial and Architecture documentation.
* **Why it works:** Now that your C++ is strong, your engine architecture is proven, and you fully understand the graphics pipeline conceptually, you can tackle Vulkan's explicit nature without being overwhelmed by graphics theory.
* **Portfolio Deliverable:** A basic Vulkan Renderer capable of setting up explicit command buffers, memory allocations, and pipelines to render a textured 3D mesh.

## The Minimum Bar for Student Jobs

For student or intern positions in graphics and engine development, companies do not expect a flawless, high-performance engine. They expect sound software engineering fundamentals and a solid grasp of vector math.

The baseline requirements include:

* **Fluency in C++ Basics:** Pointers, references, manual memory allocation, object lifetimes, and basic Standard Template Library (STL) containers must be second nature. Code readability on GitHub matters more than a massive, messy feature set.
* **Linear Algebra Foundations:** You must be able to confidently explain dot products, cross products, matrix transformations, and coordinate spaces (local, world, view, clip) during a technical interview.
* **One Completed Pipeline Project:** A working renderer showing you understand how data moves from CPU memory to the screen. Your completed CPU ray tracer or a basic OpenGL model loader fits this requirement.

## Critical Blind Spots in Your Plan

Your current resource list focuses heavily on mathematics and graphics API syntax. To transition from a student to a hireable engineer, you need to account for the practical infrastructure used in production environments:

### 1. Graphics Debugging and Profiling Tools

You cannot debug graphics code using traditional print statements or standard code breakpoints. When a shader or a buffer binding fails, you simply get a black screen. You must learn to use **RenderDoc** (essential for OpenGL and Vulkan) or **PIX/NVIDIA Nsight**. These tools allow you to capture a single frame, inspect vertex buffers, check texture bindings, and see exactly what the GPU is processing step-by-step.

### 2. Modern Build Systems (CMake)

Professional C++ development does not rely on manually linking `.lib` or `.dll` files inside IDE project menus. You need to learn **CMake** to manage your project builds and cross-platform configurations. Pair this with a package manager like **vcpkg** or **Conan** to automate dependencies like GLFW, GLM, and Assimp. Manually configuring these libraries is a massive time sink.

### 3. CPU Architecture and Memory Layout

Data structures in game engines are strictly optimized around hardware limitations. Standard deep Object-Oriented Programming (OOP) inheritance hierarchies often scatter data across memory, causing CPU cache misses that degrade engine performance. Alongside your data structures study, look into data-oriented design principles and how memory alignment impacts performance.

You should plan your first serious boot into Windows at **Month 5** (the start of your OpenGL engine), with a permanent or frequent transition by **Month 11** (the low-level API phase).

While CachyOS is fantastic for writing code, you cannot complete your game engine education entirely on Linux due to industry employment realities and platform-exclusive tooling.

## What You Are Still Missing (Learning Blind Spots)

Beyond the choice of operating system, look out for three technical requirements essential to building a functional game engine:

### 1. The PIX Profiler (Windows Exclusive)

While RenderDoc works on Linux for OpenGL and Vulkan, Microsoft **PIX** is the gold-standard profiling tool for performance tuning on PC and Xbox. It gives low-level insights into GPU execution queues, cache misses, and pipeline stalls that Linux tools cannot replicate for DirectX environments. Knowing how to read a PIX capture makes you instantly employable.

### 2. Asset Ingestion and Serialization

A game engine does not hardcode vertex arrays. It reads files. Your plan includes using `Assimp` to load 3D objects, but you need to understand how data is processed:

* **The Problem:** Parsing raw `.obj` or `.fbx` files at runtime is incredibly slow.
* **The Fix:** Real engines use a "cooking" process. You write a tool that reads the 3D asset once, converts the data into a tightly packed binary format custom to your engine, and serializes it to disk. At runtime, the engine simply does a single memory copy (`fread`) directly into GPU-accessible memory.

### 3. Math-to-Shading Application

Your math books teach you abstract concepts, but they will not explicitly bridge the gap to shader code. You must learn how to translate those formulas into **GLSL/HLSL**. For example, you need to understand how to convert your linear algebra knowledge of basis vectors into a TBN (Tangent, Bitangent, Normal) matrix inside a fragment shader to implement normal mapping.

To complete Calculus 1, 2, Multivariate, and Vector Calculus cover-to-cover in 12 months alongside your engineering goals is unrealistic. A standard university track takes 1.5 to 2 years to cover these subjects.

To make this work, you must abandon the traditional academic path and use a **targeted graphics-first approach**. You do not need to solve complex trigonometric integrals by hand; you need to understand what the calculus operations mean geometrically and how to translate them into code.

## The Adjusted Math Schedule

Integrate this specific breakdown into your daily 30–45 minute math block, aligning with your project phases:

### Phase 1 (Months 1–3): Calculus 1 — Limits & Derivatives

* **Chapters to focus on:** Stewart Chapters 1 to 4 (Limits, Derivatives, Differentiation Rules, Applications of Differentiation).
* **Engine Application:** You need derivatives to understand change over time. When building your CPU ray tracer, derivatives are used to find surface normals of complex shapes and calculate ray differentials for texture filtering.

### Phase 2 (Months 4–7): Calculus 2 & Intro to Multivariate — Integration & Partial Derivatives

* **Chapters to focus on:** Stewart Chapters 5, 6, and 14 (Integrals, Applications of Integration, Partial Derivatives). Skip Chapter 11 (Infinite Sequences and Series).
* **Engine Application:** Integration is foundational for physics engines. You will use basic numerical integration (like Euler or Verlet integration) to calculate velocity and position from acceleration. Partial derivatives are essential for understanding how texture coordinates $(u, v)$ change across a triangle's surface during rasterization in OpenGL.

### Phase 3 (Months 8–10): Vector Calculus — Fields, Gradients, and Line Integrals

* **Chapters to focus on:** Stewart Chapters 15 and 16 (Multiple Integrals, Vector Calculus).
* **Engine Application:** This is where graphics math peaks. You need to understand the gradient operator $\nabla f$ for signed distance fields (SDFs) and physics collisions. You need double integrals and line integrals to understand the Rendering Equation used in Physically Based Rendering (PBR):

$$L_o(p, \omega_o) = L_e(p, \omega_o) + \int_{\Omega} f_r(p, \omega_i, \omega_o) L_i(p, \omega_i) (\omega_i \cdot n) d\omega_i$$

### Phase 4 (Months 11–12): Numerical Methods & Revision

* **Focus:** Apply your calculus to discrete code. Computers cannot solve continuous integrals; they approximate them by sampling.
* **Engine Application:** Implement Monte Carlo integration in your ray tracer to calculate soft shadows, glossy reflections, or global illumination.
